# V1.12 交易需求复审与优化方案

日期：2026-10-14。范围：本地 V1.12 服务端策略、行情获取、事件记录、前端行情说明、信号校验、持仓提醒和现有研究脚本；参考上一轮部署校验报告。本轮没有重新核对线上文件、修改运行代码、下单或进行收益回测。结论是代码审查结论，不是实盘收益验证。

## 结论

当前具备三模型、有效入场区间、过期拒绝、真实成本补录和事件恢复的基础，但尚不满足“快速识别、可靠送达、多周期适配、可验证短线盈利”的完整需求。不能称为已经验证的国际顶级盈利系统。目标应定义为：真实成本和人工执行延迟后，在明确适用行情中仍具有样本外正期望，并且回撤和通知可靠性可量化。

| 用户需求 | 当前实现 | 主要差距 |
| --- | --- | --- |
| 震荡剥皮 | 32根15m即8小时箱体，下沿四分之一区域，最近阻力前退出 | 净TP1至少1%，会拒绝0.4%–1%的空间；缺少短周期箱体 |
| 最早突破提醒 | 5m/15m收盘确认突破 | 首次盘中突破至收盘可能等待近5/15分钟，再加行情请求、推送和人工延迟；不是突破瞬间触发 |
| 超卖触底反弹 | 空头环境、累计跌幅至少5%、一小时急跌至少3%、右侧门禁 | 适用于较大急跌；普通超卖、上升趋势回调不在当前覆盖范围；无法确认绝对底部 |
| 多周期、多时段 | 1m、5m、15m、1h；4h/12h漂移来自1h数据 | 没有独立4h结构；方向分类和路由较硬，没有状态转换缓冲、时段成本分层 |
| 盈利闭环 | 模拟路径、实际补录、退出规则 | 尚无完整同源回测、样本外证据、实际持仓后台退出推送闭环和已验收的端到端延迟 |

## 按优先级排列的发现

### P1：前端说明仍与真实策略不一致

`src/services/quantEngine.ts:815` 在宏观震荡时将1h行情交给波动分类，窗口16根代表16小时；服务端使用15m行情的16根窗口，代表4小时。前端 `:344` 起仍生成带最低值的ATR目标，`:360`、`:403` 有“锁定利润”“稳吃”等文字；`src/components/views/RadarView.tsx:116`、`:138` 展示这些目标和说明。这些不是服务端结构目标。

`src/App.tsx:260` 附近已将服务端设为唯一BUY权威，因此不能将遗留本地信号函数误报为当前正在发单；但宏观说明仍活跃，用户可能据此误解策略。前端还描述“均线回踩买点”，而服务端不提供独立回踩买入路径。应统一服务端市场状态与规则快照，删除收益保证文案，隔离未调用的旧策略代码。

### P1：窄幅震荡需求与1%最低净目标冲突

`scratch/remote_scanner_daemon.py:79` 的 RANGE 最低净TP1为1%；`:1683` 要求8小时稳定箱体；`:1721` 严格审查最近阻力并扣0.11%。这能避免虚构目标，但会自然过滤小空间机会。不能靠取消成本、跳过近阻力、压缩止损解决。

建议在研究环境建立 RANGE_MICRO 子策略：短周期稳定区间、下沿止跌、最近均衡位或阻力前退出；研究最低净空间0.40%至1%这一段，仍遵守项目0.40%和净RR1.10底线。原1%–4%规则保留作为独立基线。若真实可交易空间小于0.40%，按现有规则就是放弃，不承诺所有窄幅行情都能剥皮。降低原1%门槛属于策略变更，不能因本审计自动上线。

### P1：“每2秒扫描”不等于两秒内提醒

服务端 `:1967` 主循环顺序获取ticker、1h、15m、5m、1m和depth，最后再休眠2秒；接口超时及备用地址重试会进一步延长周期。`:1542` 只接受已收盘突破。客户端的WebSocket不会加快服务端判定。

建议服务端建立WebSocket行情缓存、事件驱动计算和独立通知队列；REST用于初始化及缺口恢复。结构与未收盘触发分开：提前关注不是买入；盘中早触发作为单独实验变体，不能冒充已收盘确认。保留收盘确认基线并比较延迟、假突破和净收益。

### P1：进场成本估计仍固定，补录只解决事后核算

服务端 `:67` 与客户端 `src/services/signalValidity.ts:3` 的入场准入仍扣固定0.11%。V1.12实际成交成本计算不等于策略已经按用户费用和下单规模动态评估。需要分开实付费用、盘前估计费用、价差、深度冲击和人工延迟；未知值标注不确定，不能默认为零。使用ask/bid成交模型时，不得再次重复扣同一价差。

### P1：买入推送没有形成实际持仓退出推送闭环

服务端 `:2042` 为买入候选调用FCM；实际补录用于账本计算，现有后台没有对应实际持仓的止损、失效、分批止盈、到期通知服务。`src/services/positionRules.ts` 和持仓页面主要给出前台规则提示。服务端参考路径不是用户真实库存。建议基于用户确认的持仓与成交建立后台管理，只提醒剩余仓位，退出提醒使用独立事件类型，不引入做空信号。

### P1：尚无策略盈利验证体系

`scripts/backtest_btc.py` 是V1.07数据检查工具，明确不计算生产信号数量和胜率。现有单元测试证明特定实现行为，不证明市场优势。需要同一策略函数支持实时与回放，按时间做训练、验证、最终留出测试；对重叠持仓做隔离，训练参数冻结，记录尝试次数。没有历史盘口不能编造盘口门禁，必须将K线结构研究与真实盘口前向检验分开。

### P2：多周期路由和算法定义需要更清楚

服务端 `:1403` 主要用1h均线、RSI、固定漂移和24h变化分类。`:1840` 附近优先突破，再空头反弹，再震荡，缺少过渡态和状态滞回。较慢的24h跌幅可能阻止已经改善的局部行情；增加分类复杂度是否有益必须比较基线，不能凭感觉堆指标。

`:1073` RSI是最近14个涨跌的简单平均，`:1095` ATR是最近14个TR的简单平均，并非Wilder平滑口径。不是天然错误，但应显式命名与版本化，避免拿其他平台同名指标直接对照。RSI背离使用前后分段最低点，需要验证锚点稳定性。15m波动样本约一天且滑窗重叠，不能把这些窗口视为独立样本来推断置信度。

五类防飞刀检查目前分散在瀑布过滤与函数内四类门禁，不应仅因函数中只有四个注释就断言没有第五类；应输出五类独立检查结果、数据时间和拒绝原因。单次20档挂单失衡不是持续主动买入，更不是价格将上涨的证据。

### P2：运维与通知可靠性

行情、扫描、推送在同一主循环；进程存活不能证明行情新鲜或每个后台线程健康。HTTP共享令牌接口、前端含凭据等现有访问方式不适合长期存放实际成交隐私数据。建议TLS、设备级认证、请求限流、密钥外置、心跳和停滞报警；策略计算与推送故障隔离。先采用模块化单体和SQLite事务/outbox即可，不必为了单个BTC标的引入复杂分布式集群。

## 推荐目标结构

币安同一现货市场行情 → 带时钟/序列/缺口检查的缓存 → 多周期市场状态 → 三策略族 → 成本与风险门禁 → 信号生命周期及持仓管理 → 持久通知队列 → APP复核与补录。所有判定写入可回放事件库。

1. **震荡族**：区分微区间与较宽区间；低位止跌才准入，箱体破坏立即失效，出场依据实际阻力。微区间的最长持有时间作为实验参数，不硬套4小时。
2. **趋势族**：压缩蓄力观察、突破触发、收盘或回踩确认三阶段；趋势回踩作为同族可选变体。无可验证上方阻力的新高行情继续拒绝正式交易，跟踪退出仅作独立研究，不能虚构TP通过原门禁。
3. **反弹族**：暴跌右侧反弹保留；普通超卖恢复作为独立实验变体。用波动标准化跌幅做候选研究，不能仅以RSI低就买；强空头和流动性异常时允许完全不交易。
4. **周期职责**：4h/1h提供背景风险，15m确定结构，5m形成机会，1m及成交流触发。不要要求所有周期永远同向；明确每个模型允许的组合和否决条件。亚洲/欧洲/美国时段、周末只作为分层统计和成本信息，未经样本外验证不独立调参。
5. **账户风险**：给定用户风险预算、实际可用余额和已有库存才计算仓位上限；缺信息不伪造建议金额。限制同向机会叠加、亏损后重复入场，日内风险触发时暂停新入场但保留退出管理。不自动下单。

## 验收标准

工程先验收：确定性回放、无未来函数、行情断流关闭新入场、订单簿序列重建、重复事件不重复提醒、断网重启恢复、实际持仓部分退出、过期撤销、前后端同源展示。记录交易所事件、服务端收到/判定/发送、手机收到/打开、人工成交时间，缺失项保留未知。先测基线，再制定延迟预算；如缓存到判定p95≤500ms只能作为待验证工程目标，不能承诺手机必达。

策略再验收：按模型、市场状态和时段报告净期望、收益因子、回撤、连续亏损、MAE/MFE、机会数量、送达及成交转化、延迟敏感性。样本外净期望及其按时间块估计的区间、独立交易数量、费用压力场景、参数稳定性一起报告；区间跨零就是证据不足。至少覆盖多个行情阶段，不能用少量交易、单个上涨阶段或任意“30天”宣称验证成功。交易少就延长观察，不为凑样本降低标准。

优先顺序：①修复说明与统一状态；②采集行情/延迟并建立同源回放；③补齐实际持仓退出与风险闭环；④三族新变体影子比较；⑤达标后逐项启用。最优参数和最高胜率目前未知。
